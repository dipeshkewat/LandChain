1. Product Definition
1.1 Product summary
LandChain is a web application prototype for registering property records, recording the current on-chain owner, validating owner-initiated ownership transfers, maintaining a transaction history, and checking document integrity through SHA-256 hashes. Solidity smart-contract rules are the enforcement layer for registration and transfer operations. PostgreSQL stores searchable application metadata and indexed/cached event information.
1.2 Problem statement
Land-record workflows can involve fragmented records, slow verification, unauthorized modifications, duplicate entries, and difficulty tracing ownership changes. LandChain demonstrates how smart contracts and tamper-evident event histories can improve traceability and make unauthorized state changes detectable.
1.3 Objectives
Register unique property identifiers and initial owner addresses through an authorized smart contract function.
Allow only the currently recorded owner to initiate a valid ownership transfer.
Display recorded ownership and a traceable history of registration and transfers.
Generate and compare SHA-256 document hashes to detect byte-level content changes.
Build a usable web dashboard with property search, transaction status, and verification results.
Test authorization failures, invalid inputs, duplicate IDs, and database/blockchain consistency.
1.4 Scope and explicit limitations
Included: property registration, property search, owner lookup, owner-initiated transfer, document hash verification, transaction history, admin dashboard, API, and PostgreSQL metadata.
Excluded: official government registry integration, legal title adjudication, production identity verification, real-estate payments, legal dispute resolution, and production deployment.
The application demonstrates recorded ownership on its blockchain. It does not establish legal ownership or prove that submitted documents are genuine.
Do not store personal identity documents, full deeds, private keys, or sensitive owner data on a public blockchain.
The first target is a local educational prototype. Do not describe it as production-ready.

          | blockchain adapter / ethers.js

PostgreSQL is used for searchable property metadata, user accounts, private document references, transfer transaction tracking, and indexed event data. The contract is authoritative for the on-chain property owner and contract-level rules. Cached database fields must be reconciled against contract state/events.
3.1 Transaction flow
A user opens the registration form and submits property metadata and a document.
The backend validates the request, computes SHA-256 over the uploaded file bytes, and saves an off-chain metadata record in a pending state.
An authorized admin submits the contract registration transaction. Do not mark the record confirmed before the transaction succeeds.
After confirmation, save the transaction hash and reconcile the property state/event into PostgreSQL.
For transfers, the current owner's wallet signs and submits the transaction. The contract validates msg.sender and recipient address.
The backend records transaction status and synchronizes confirmed events. If the chain operation fails, the UI must show failure and must not claim ownership changed.
For verification, hash the supplied file bytes and compare the hash to the registered on-chain document hash.

7.1 API conventions
Return consistent JSON error objects with a safe message and HTTP status code.
Validate path parameters, addresses, strings, numeric values, file types, and upload size.
Use pagination for property listings and transaction history.
Protect admin routes with authentication and role checks.
Do not trust a client-supplied owner address as proof of wallet ownership.
Use a wallet signature or a transaction sent from the current owner address for owner-authorized operations.
For browser wallet flows, let the wallet sign the transaction; never ask for a private key or seed phrase.
Make repeated requests idempotent where possible and handle pending transactions explicitly.

9. Document Hashing
Compute SHA-256 over the exact uploaded file bytes, producing a 32-byte digest. Store the digest on-chain as bytes32 and store the 64-character hexadecimal form in PostgreSQL. Use one documented normalization convention, such as lowercase hexadecimal without a 0x prefix in the database.
Conceptual flow:
file bytes -> SHA-256 -> 32-byte digest
                         |
                         +-> bytes32 sent to contract
                         +-> 64-character hex stored off-chain
 
Verification:
uploaded bytes -> SHA-256 -> compare to registered on-chain digest
Use the same raw-byte hashing method for registration and verification.
Do not hash a filename or file path instead of the file contents.
A one-byte change should produce a different digest with overwhelming probability.
A mismatch means the file bytes differ from the registered file bytes; it does not by itself prove fraud.
Keep full deed files off-chain and private. A hash can itself reveal equality or enable guessing attacks for predictable documents; consider access and privacy implications.
